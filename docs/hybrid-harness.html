Jev + LLM · worked example

Two dials, not one

A support-ticket harness where Jev decides and its confidence decides who decides. Running it across 40 tickets turns up something the architecture diagrams never show: the two thresholds are independent dials controlling different costs. One buys accuracy. The other buys money. Moving the wrong one does nothing.

01 · The mechanism

One Jev call, three destinations

The ticket goes to Jev once. Three questions ride in that single request and come back answered in parallel. The confidence on the primary question gets compared against two cut points that live in your code — and those two cuts are the whole routing policy.

That is the finding. Drag dial 1 and errors shipped moves while cost sits perfectly still. Drag dial 2 and cost swings by two orders of magnitude while errors never budge. Most write-ups on this pattern describe "a confidence threshold" as if it were one knob trading one thing. It is two knobs trading two unrelated things, and knowing which one you are holding is the difference between fixing your budget and fixing your error rate.

03 · The economics

Your savings are capped by your escalation rate

Jev costs roughly a thousandth of an LLM call. That ratio is irrelevant. What decides your bill is the fraction of traffic you don’t send onward — so the headline multiplier collapses the moment escalation climbs.

The 772× at the left edge is not a real operating point — it is what you get when nothing escalates, i.e. when you have quietly turned the LLM off and are trusting a classifier with everything. The honest range for a harness that actually escalates its uncertain cases is the 2–8× band in the middle. Any vendor multiplier quoted without an escalation rate attached is describing the left edge of this curve.

04 · The code

What the seam actually looks like

The escalator is an ordinary async function returning the same type the Jev path returns. That substitutability is the design: callers never branch on which engine answered.

// The LLM is constrained to the same shape Jev guarantees structurally.
const response = await client.messages.create({
  model: "claude-opus-5",
  max_tokens: 1024,
  output_config: {
    effort: "low",              // triage is classification-shaped
    format: { type: "json_schema", schema },
  },
  messages: [{ role: "user", content: prompt }],
});

And the call site cannot get the band wrong, because DecisionResult is a discriminated union with no outcome on the root:

switch (result.kind) {
  case "acted":     return commit(result.outcome);          // no LLM was called
  case "review":    return prefillForHuman(result.outcome); // provisional only
  case "escalated": return commit(result.outcome);          // the LLM answered
  case "fallback":  return commit(result.outcome);          // Jev down, rules ran
  case "failed":    throw new Error("no fallback defined");
}

05 · What this is not

Read the caveats before you quote the numbers

  • Both models are simulated. No TypeSafe key and no ANTHROPIC_API_KEY were available. The routing, the banding and the arithmetic are real code running on real data; the model outputs come from a deterministic stand-in calibrated to the published benchmark shape (100% on clear cases, ~71% on ambiguous).
  • Jev’s price is unverified. The $0.042/M input figure appears only in secondary blogs and could not be confirmed from any first-party TypeSafe source. Every cost number here inherits that uncertainty. LLM pricing is first-party and solid.
  • The escalate band’s final accuracy is not modelled. The stand-in passes Jev’s guess through rather than inventing an LLM that magically knows the answer. So "errors shipped" counts only the auto-act band — which is the number that actually matters, because it is the one nobody downstream checks.
  • 40 tickets is far too few to set a real threshold. The eval harness in this repo refuses to suggest one below 50 for exactly this reason.
