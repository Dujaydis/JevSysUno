# The Jev wire contract (verified)

**Provenance.** `typesafe.ai` and `docs.typesafe.ai` were unreachable from this research
environment (egress policy block). Everything in this file was instead read directly from
**TypeSafe's own official SDK source code**, cloned from the `typesafe-ai` GitHub org. The
Python SDK's wire models carry the header `# generated by datamodel-codegen: filename:
https://api.typesafe.ai/openapi.json`, so these field names are machine-generated from
TypeSafe's real OpenAPI spec — this is first-party and exact, not a blog's paraphrase.

Anything that could *not* be confirmed this way is marked **UNVERIFIED** and must not be
hard-coded.

## Transport

| | |
|---|---|
| Base URL | `https://api.typesafe.ai` (override: `TYPESAFE_BASE_URL`) |
| Inference | `POST /v1/systemone` |
| Model list | `GET /v1/models` |
| Auth | `Authorization: Bearer $TYPESAFE_API_KEY` |
| Default model alias | `jev-latest` (override: `TYPESAFE_DEFAULT_MODEL`) |

Response headers the SDKs read: `x-typesafe-request-id` (quote this in support requests),
`retry-after` / `retry-after-ms` (429 backoff).

## Request

```jsonc
{
  "state":     "...",        // string | JSON object | array — the content ALL questions refer to
  "model":     "jev-latest", // name or alias; GET /v1/models lists them
  "questions": { /* name -> Question, at least one */ }
}
```

`state` is **top-level and shared**. It is not repeated per question. Every question in the
request is answered against this same state, independently.

### Question shapes

```jsonc
// Noul — does this condition hold?
{ "type": "noul",
  "instructions": "Is this ticket about billing?",   // optional
  "criteria": { "true": "...", "false": "..." } }    // optional, describes each outcome

// Choice — which one of these? criteria is a MAP (label -> description or null)
{ "type": "choice",
  "instructions": "What is this ticket about?",
  "criteria": { "billing": null, "technical": null, "other": null } }

// Score — how much, on an ordered rubric? criteria is an ORDERED LIST, index = level from 0
{ "type": "score",
  "instructions": "How urgent is this ticket?",
  "criteria": ["can wait", "this week", "today", "right now"] }
```

Two mistakes the SDKs will catch for you, because they are easy to make:
- Passing a **list** to `choice` → error. Choice criteria are a map.
- Passing a **map** to `score` → error. Score criteria are an ordered list.
- `score` requires **at least two** levels (JS SDK enforces ≥2; the Python SDK only
  enforces ≥1 — an SDK-level inconsistency; write ≥2 either way).

Unknown fields on a question object are rejected client-side (`extra="forbid"`).

## Response

```jsonc
{
  "model": "jev-latest",
  "answers": { /* same keys you used in `questions` */ },
  "usage": { "input_tokens": 120, "output_tokens": 12 }
}
```

### Answer shapes — discriminated on `type`, mirroring the question

```jsonc
{ "type": "noul",   "noul": 0.98 }

{ "type": "choice", "choice": "angry", "confidence": 0.8,
  "probabilities": { "angry": 0.8, "calm": 0.1, "excited": 0.1 } }

{ "type": "score",  "score": 1.7, "confidence": 0.8,
  "legend":        { "0": "can wait", "1": "this week", "2": "today" },
  "probabilities": { "0": 0.1, "1": 0.1, "2": 0.8 } }
```

Note: **Noul has no `confidence` field.** This is deliberate, not an omission — the
probability itself carries the uncertainty. Asking "what's the confidence of this
probability" is a category error.

On the wire, Score's `legend`/`probabilities` keys are **strings** (`"0"`, `"1"`). The
Python SDK coerces them to `int` in its ergonomic wrapper; the JS SDK leaves them as
string-keyed. Watch this if you write cross-language code.

## Billing

`usage.output_tokens` carries this OpenAPI-generated field description, verbatim:

> "Number of output tokens used to answer the questions. **Output tokens are currently
> free of charge.**"

That is the *only* pricing-adjacent statement confirmable from a first-party source. The
widely-repeated **$0.042 / 1M input tokens** figure appears only in secondary blogs —
**UNVERIFIED**. Do not hard-code it into billing or budgeting code.

## Errors

| Status | JS / Python | Note |
|---|---|---|
| 400 | `BadRequestError` | |
| 401 | `AuthenticationError` | bad/missing key |
| 403 | `PermissionDeniedError` | |
| 404 | `NotFoundError` | |
| 422 | `UnprocessableEntityError` | body is `{detail: [{loc, msg, type, input, ctx}]}` |
| 429 | `RateLimitError` | exposes `retry_after_ms` |
| ≥500 | `InternalServerError` | |

Plus transport-level `APIConnectionError`, `APITimeoutError`, `APIUserAbortError`.

## SDK defaults worth knowing

Retries: `maxRetries: 2`, exponential backoff 500ms → 5s cap, 25% jitter, honors
`Retry-After` up to 60s, retries 408/429/5xx plus connection and timeout errors.
Timeout: **10s per attempt, with no total retry budget** — so a pathological call can
occupy ~30s of wall clock. Set your own ceiling if that matters.

## NOT FOUND — do not invent these

Context window · max questions per request · max payload size · numeric rate limits ·
concrete pricing · the model version list behind `jev-latest` · any determinism guarantee ·
how to obtain an API key (console URL). Secondary sources claim 32k context, 32
questions/64KiB, 250k tok/s + 1200 rpm, and a `jev-1.13` version — **none confirmed**, and
one such claim ("no automatic retries") is flatly contradicted by the SDK source.
